条目 D016（O-1 的最小修法）—— S3 要实施的修复，本轮只做准备

（a）修改点与建议代码形状
  位置（按内容）：S4/pattern/pattern.c 中函数 pattern_generate_flow_field，
    在语句 "max_field = 1./max_field;" 之前（H 树约第 2145 行；B 树行号不同，按内容定位）。
  前置事实（[源码]）：
    - max_field 来自两分支之一的返回值：pattern_generate_flow_field_rect（约 1638 行）或 _tri（约 2086 行）。
    - 两者的 max_field 都以 0 初始化，仅在 af > max_field 时更新（rect 1624/1633，tri 2061/2080）。
    - 因此场为零时 max_field = 0；场元素全为 NaN 时（比较为假）也返回 0。
    - 现在的 "1./max_field" 对 0 得到 Inf，随后 field *= Inf，产生 NaN 或 Inf 写入 vfield。
  建议形状（伪代码，不写入 S4/）：
      if(!(max_field > 0) || !isfinite(max_field)){   // catches 0, negative, NaN, Inf
          return <ERRCODE>;                            // no multiply on the field
      }
      max_field = 1./max_field;
      ... (existing loop unchanged) ...
      return 0;
    说明：!(max_field > 0) 同时覆盖 0 与 NaN（NaN > 0 为假）；isfinite 覆盖 Inf。
    返回前不写 field（field 在 rect/tri 中已被写入；调用方在 error != 0 时释放 vfield，内容不被使用，见第 (c) 节的 NV 风险）。
  证据类型：[源码] 前置事实；建议形状 [推断]（待 S3 实施后验证）。

（b）错误码选取
  现有码（[源码]，H 树）：pattern_generate_flow_field 的参数检查为 -1 至 -8（pattern.c 2099–2106）。
  -9 的占用（核对命令与结果，见下方"核对记录"）：
    - S4/pattern/pattern.c:1066 有 "return -9"，属于 pattern_discretize_cell 的 NULL == value 检查（[源码]）。
    - pattern.h 与 fmm_PolBasisVL.cpp、fmm_PolBasisJones.cpp、fmm_PolBasisNV.cpp、S4.cpp 中无 -9 的使用（[源码] grep）。
  结论：-9 在 pattern_generate_flow_field 的作用域内未被占用，但在 pattern.c 全文件中已被 pattern_discretize_cell 占用。
  建议：使用 -9，理由：三个调用方与 ComputeLayerModes 只关心非零（[源码]：if(0 != error)），不区分具体负码，故码值重复不引起误判。
  但需要注意：pattern_discretize_cell 的 -9 与新 -9 在同一文件中含义不同。若 S4 将来需要区分，应选下一个空闲值（-10，已核对 pattern.c 中 -10 未出现；见核对记录）。
  需要用户批准：错误码取值（-9 或 -10）。

（c）调用方一致性（详见 J6C_CALLER_CONSISTENCY.txt）
  - VL、Jones：error != 0 时释放 vfield、work、ivalues（各带 NULL 检查），return error。无遗漏、无重复释放（[源码]）。
  - NV：先归一化 vfield（对未写入的 vfield 做除法，风险 R-NV-1），后检查 error。这是不一致的顺序（[源码]）。
  - 风险 R-NV-1 不是 D016 引入的，但 D016 修法后仍会经过它。建议 S3 把 NV 的 error 检查移到归一化之前（需用户批准，位于 FMM 路径内）。

（d）修后预期（三树 B/A/H；VL NB=1–4，即 n_G=1）
  前提（证据等级）：
    - VL n_G=1 时 pattern_generate_flow_field 返回 0：[实测] 本轮 J6_NG1/（B、A、H 各 1 次，eax=0）。
    - max_field = 0、vfield = NaN、1./max_field = inf：[实测] 引自 P05_S1R_O1_ATTRIBUTION.md 第 71–72 行（S1R 的 gdb 观测；本轮未重算 max_field 的数值，
      因 _rect 无符号、field 参数布局在本轮 gdb 中未能可靠读取，见 J6_NG1/ 说明）。
    - Jones、NV 在 NG=1 的 max_field = 0.0402（非零）：[实测] 引自同一文件第 79 行。
  注：以下修后预期全部为 [推断]，因为修法未实施，不能在未改源码的情况下观测。
  - 失败发生位置：pattern_generate_flow_field 的新检查（max_field 为零），经 VL 的 if(0 != error) 路径返回。
  - 不再发生：场乘以 Inf（field 不再被写为 NaN）；NaN 不再进入 PolBasis 的 Epsilon_inv 与 Epsilon2（失败发生在 vfield 生成之后、写 Epsilon2 之前）。
  - 驱动 rc：预期仍为 20（ComputeLayerModes 把 PolBasis 的任何非零返回映射为 20，H 树 S4.cpp 2413–2417 行）。[推断]
  - 公共 API 异常文本：预期仍为"层特征系统无法求解"（码 20，main_python.c:137）。[推断]
    其中 info=2 的 TRACE 文本（若在 TRACE 构建中出现）预期不再出现，因为求解不再进行。[推断]
  - 最终错误码（驱动与公共 API 层）：预期仍为 20，不是新的码。新码只出现在 ComputeLayerModes 之前的 TRACE 中。[推断]
  - Jones、NV 在 NG=1：max_field 非零（8×8 网格，[实测] 见 S1R 归属文件），预期行为不变。[推断]
  - VL NB=5–9：max_field 非零，预期不变。[推断]

（e）验证方法建议（留给 S3 与 S4，不在本轮实施）
  1. VL n_G=1（NB=1–4）：用 J1 的 gdb 方法（SolveLayerEigensystem 入口读取 Epsilon2）观测，修后应不到达求解（入口计数 = 0 或仅来自其他层）。
  2. VL NB=5–9、Jones、NV：与修前做正常路径的字节一致比对（驱动输出与 FieldPlane 结果的 sha256 逐字节一致）。
  3. 三树（B、A、H）均测；B 树的 VL 在 NG=1 同样经过 pattern_generate_flow_field，修法须在三树都生效。
  4. 对新检查的单元测试：构造全零场的 pattern（例如 nshapes=0 不走此路径；需要一个非零形状但场为零的几何，须先找到该几何）。[未验证：本轮未找到可复现的全零场几何以外的触发方式]

  证据类型：[实测]（求解器入口 NaN、栈追踪、退出码）；机理（溢出 vs 除零）[推断]，未逐元素确定。

    需先定义阈值与语义（物理上合理的材料对比范围），这是需要用户决定的事项。
  预计涉及文件：S4/fmm/fmm_kottke.cpp；可能涉及 S4/S4.cpp（ComputeLayerModes 的非有限检查）。
  需要用户批准：(1) 阈值与语义；(2) 是否在 ComputeLayerModes 加通用的非有限检查（影响面更大，属 S4 阶段）。
  未验证：张量材料路径（D7 的 fill·abcd10 + (1-fill)·abcd00 = 0 条件）只测了一个非正定张量（P2-B），正常返回；可达性未证实。
