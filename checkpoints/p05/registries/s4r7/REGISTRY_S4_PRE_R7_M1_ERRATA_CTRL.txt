1. The defect (generator and runner, both wrong in half):
   make_prereg_m1_r7.py writes the label CONTROL_OK into column first_expected_class and the rc string
   "rc_first=..,rc_retry=..,run_rc=.." into column expected_class (the header order is point_id ... first_expected_class,
   expected_class, expected_win1_rc, basis, status; the row values are shifted relative to the intended columns).
   run_m1_r7.py reads the rc string from column expected_win1_rc (which holds "-" for controls), and it requires
   expected_class == CONTROL_OK.  So every control is scored MISMATCH by the runner while the observed values are correct.
   (An earlier version of this errata said the rc string was in first_expected_class; that was wrong, and is corrected here.
   The registry file itself is not edited.)

   a. The row is MATCH-TO-REGISTRY when observed rc_first (RC first), rc_retry (RC retry) and run_rc equal the registered
      string AND hit = 0 (no injection reached).
   b. The label is CONTROL_OK when, in addition, rc_first = rc_retry = run_rc = 0 (the judge's clean-control rule,
      judge_d003.classify, control=True).

      does NOT define rc 20 as CONTROL_OK (it returns INVALID "control run not clean"), so these two modes are not CONTROL_OK.
