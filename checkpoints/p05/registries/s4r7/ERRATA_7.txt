== E7-3  closed mode name in the no-injection equivalence (step 4.3)
The first run of run_noinject_equiv_r7.sh (RESULTS_R7_NOINJECT_run1.tsv) used the mode name "closed".  driver_r6b_state
accepts "closed2d" and "closed1d" only; "closed" makes the driver exit with rc 2 ("S4FMM ARGERROR invalid or missing FMM_MODE=closed")
on BOTH F and F2, before any field is computed.  This produced 9 NOT_IDENTICAL_OR_MISSING rows (closed x NG 1/5/9 x call1-3).
These rows are a mode-name input error on the executor's side, NOT a difference between F and F2 output.
The file run1 is kept unchanged (U17).  The correction is a labelled follow-up run "run1b" with mode closed2d on F and F2:
all 9 dump comparisons (NG 1/5/9 x call1-3) are IDENTICAL, rc 0 on both trees.  The 108 other run1 rows are IDENTICAL.
Consequence for the gate of step 4.3: the only non-IDENTICAL rows are explained as input error, and the corrected mode is IDENTICAL.
No injection was run before this explanation.

== E7-5  seam diff method (step 3.3)
The seam diff comparison compares the content lines of "diff -ru" between each seamed tree and its own clean tree, after removing the
header lines (diff -ru, +++, ---), because those lines carry absolute paths and timestamps.  Result: seamF and fmmret content diffs
are IDENTICAL between F and F2 (237 and 72 lines).  Recorded in SEAM_DIFF_F_vs_F2_R7.txt.  The brief asked for "diff identical";
the header stripping is the only change of method and is stated here.

== E7-8 M1 pre-registration column error (control rows; found after pass 1, before pass 2 was judged)
REGISTRY_S4_PRE_R7_M1.tsv (generated by testing/d003/stage_s4r7/make_prereg_m1_r7.py, sha256 db529573...cf53cf3, UTC 2026-10-12T11:05:20Z)
writes the 18 CONTROL rows with the expected rc string ("rc_first=..,rc_retry=..,run_rc=..") in column first_expected_class,
while run_m1_r7.py reads it from column expected_win1_rc, which holds "-" for controls.  The runner therefore reports
"control expectation not defined in pre-registration" and scores all 18 control rows MISMATCH.
What was checked (read only, after both passes): for every control, observed rc1, rc2 and run_rc EQUAL the values in the
registry string (18/18 equal; for example vl NG1: rc1 20, rc2 20, run_rc 0).  So the S4 behaviour matches the expectation in all
18 controls; the MISMATCH is a registry/runner column error, not a result.
Decision: the registry is NOT edited after the runs (it was hashed before the first run; AGENTS section 5).  The 18 control rows
stay MISMATCH in RESULTS_R7_M1_pass{1,2}_run2.tsv and are reported as MISMATCH (column error) in REGRESS_R7_M1.tsv.  The user decides
whether this counts as a defect of the pre-registration (recommended: a generator error, to be fixed in a new ERRATA and re-judged
from the same stored outputs in M2 or on request).  No injected point is affected: the 90 non-control rows all judge as expected.

== E7-10 gdb chain method (section 5)
'finish' stops the program at the first return of each breakpoint, so a finish-based run never reaches the injection path
beyond the first breakpoint (observed in the first two jones attempts: only Simulation_ComputeLayerModes printed, rc 0).
The judged chain therefore uses a continue-only run (gdb_chain_jones_entry_r7.gdb), and return values are read in a separate
finish run (gdb_chain_jones_finish_r7.gdb).  Consequence: for every chain run, FMMGetEpsilon_PolBasisJones' RETURN VALUE is 未读到
(its finish breakpoint is never reached in the finish run).  Recorded in GDB_CHAIN_SUMMARY_R7.tsv; not filled from source.
