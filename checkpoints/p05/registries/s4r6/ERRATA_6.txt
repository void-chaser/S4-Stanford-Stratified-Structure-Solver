== E6-3 [PLANNER CORRECTION U5a] R5 "failed layer kept no partial modes FAILED / partial_modes=1" is NOT defect evidence ==
R5 (E5-15, R5 report section 7, RP-R5-3) reported that the driver check "failed layer kept no partial modes" FAILED in 132/132
retry runs with partial_modes=1.  The planner's reading of driver_d003.cpp (checked at the R6 gate):
- driver_d003.cpp line 220 (the retry call, rc2 = S4_Simulation_GetFieldPlane) runs FIRST.  Verified at the R6 gate with grep -n.
- The partial_modes count (driver_d003.cpp lines 253-255: the loop over S->layer[i] that tests modes != NULL; the check is at line
  257) runs AFTER the retry.  (The planner's first note said "lines 253-257"; the verified range is 253-257 as well, with the count
  at 253-255 and the check at 257.  No change of meaning.)
- A successful retry necessarily installs the modes of the layer that the retry computed.  Therefore a non-NULL layer modes pointer
  after the retry is expected behaviour of a successful retry, not evidence of a failure-time state.
- The check therefore cannot observe the state AT the failure.  It tests the post-retry state.  It is not a test of the
  requirement "a failed layer installs no modes" (S3-4b).
Consequence: RP-R5-3 is re-classified as a harness fault of the driver check (HARNESS_OR_PROCESS), not as a candidate red point.
The S3-4b requirement stays OPEN; R6-2 tests it by observing the state at the failure instant (driver_r6_state).
Note: the R5 line numbers quoted above are those of driver_d003.cpp (the template); the exact line numbers are verified in R6-2 by reading
the file, and are recorded there.

== E6-8 [USER RULING, contract semantics for I2; known before any R6-2 state run; status INFLUENCED] ==
Source of the question: a read-only probe (closed1d malloc NTH 1 on tree F, route once, injection in layer 1 Slab, rc1 = 20)
showed that at the failure instant the failed layer (layer 1, Slab, nshapes 1) has modes == NULL, while layers 0 and 2 (uniform
layers, computed before the failing layer) already have non-NULL modes.  S4_internal.h:263 says "20 - the layer eigensystem failed;
no layer modes or solution were installed", which read literally conflicts with the layers 0 and 2 state.
User ruling (in conversation, R6 gate, recorded here):
  (1) I2 uses option 1: only the failed layer must have modes == NULL (I1); the request-layer solved == 0 (I4) must hold strictly.
      Other layers that finished before the failure may keep their modes and this is NOT a violation, provided ALL of:
        (a) the q hash of each kept layer equals the control-group q hash at the same instant;
        (b) the control group has the same layer installed at the same instant (no layer installed only in the failure run);
        (c) on the retry those layers do not enter ComputeLayerModes again (checked by the I5 call counts).
  (2) Basis: the comment at S4_internal.h:263 originates from commit 44f4a09 (P04 D001/D002).  That commit's text reads, for S4.cpp:
      "a failed eigensolve discards the layer modes instead of installing them" (verified read-only with git log -1 44f4a09).
      It refers to the failed layer.  It does not state the behaviour of other, successful layers.
  (3) Recording: the wording mismatch between the comment at S4_internal.h:263 and the observed behaviour is registered in the R6
      ledger as HARNESS_OR_PROCESS (documentation wording), with a suggested wording.  S4/ is NOT changed in R6.
  (4) Pre-registration: REGISTRY_S4_PRE_R6_TWICE.tsv is NOT changed by this ruling (it concerns R6-1 only).  The R6-2 state
      pre-registration, when written, must state I2 as above.  No existing pre-registration file is edited.
Suggested wording for S4_internal.h:263 (NOT applied): "20 - the layer eigensystem failed; the failed layer's modes and solution
were not installed (layers finished before the failure may keep their modes)."
